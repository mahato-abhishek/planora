1. What Planora Does

Planora is an authenticated workspace for managing projects, tasks, deadlines, and progress. A user signs in, sees a dashboard summary, manages projects and tasks, moves tasks through statuses, and uses a calendar to understand upcoming work.

Area What it provides Main route
Landing page Product introduction, screenshots, feature explanation, workflow, demo entry point /
Authentication Email/password, Google OAuth, demo login /auth
Dashboard Counts, recent projects, recent tasks, quick action /dashboard
Projects Create, edit, delete, filter, progress display /dashboard/projects
Tasks Create, edit, delete, filter, list view, Kanban drag/drop /dashboard/tasks
Schedule Interactive monthly calendar and selected-day agenda /dashboard/schedule

2. High-Level Architecture

Browser | | Next.js App Router navigation v Layouts and pages in app/dashboard/ | | Server Components fetch authenticated data v Server actions in lib/actions/actions.ts | +--> getUser() -> Better Auth session | +--> Drizzle ORM queries | v PostgreSQL / Neon Client components receive server data | +--> local UI state: filters, modals, view mode +--> server actions: create, edit, delete, status changes +--> dnd-kit: Kanban drag/drop

Pages own server-side data loading. Interactive components use "use client" and receive typed data as props. This keeps database access on the server while allowing responsive UI interactions in the browser.

5. Authentication

Authentication is provided by Better Auth with a Drizzle adapter.

Configuration

lib/auth.ts sets:

  • baseURL from BETTER_AUTH_URL.
  • basePath: "/api/auth".
  • Email/password authentication.
  • Google social provider.
  • nextCookies() integration.

The route handler at app/api/auth/[...all]/route.ts exposes Better Auth GET and POST handlers.

Email flow

AuthClientPage -> signIn(email, password) -> auth.api.signInEmail() -> Better Auth creates/loads session -> router.push("/dashboard")

Google flow

signInSocial() asks Better Auth for an authorization URL and returns it to the client. The browser navigates to that URL. This avoids treating a server redirect as a normal return value.

Google Cloud Console must include the matching callback URL, normally: 

http://localhost:3000/api/auth/callback/google

Session reuse

getUser() is wrapped with React cache(). This memoizes the authenticated user within a request so the dashboard layout and data actions do not repeat the same session lookup unnecessarily.

6. Dashboard

The dashboard page loads projects and tasks in parallel:

const [projectData, taskData] = await Promise.all([
  getProjectData(),
  getTaskData(),
]);

This avoids waiting for the project query before beginning the task query.

Dashboard layout

app/dashboard/layout.tsx protects the workspace by checking getUser(). On large screens, the layout has a fixed viewport-height sidebar and independently scrollable main area. On small screens, the desktop sidebar is hidden and MobileNav provides a fixed bottom navigation bar.

Summary cards

dashboard-overview.tsx computes:

  • Total projects.
  • Total tasks.
  • Tasks in progress.
  • Tasks in review.
  • Completed tasks.

The cards are responsive: one column on small screens, two columns at medium widths, and five columns on large screens.

Recent panels

recent-projects.tsx and recent-tasks.tsx display a maximum of five items each. They retain “View All” links so the dashboard stays compact without hiding data.

7. Projects

The projects page loads project rows and compact progress aggregates in parallel. A project card contains:

  • Project name and type.
  • Priority badge.
  • Completed/total task progress.
  • Description.
  • Edit and delete actions.

getProjectProgress() uses a grouped database query instead of loading every task row into the projects page. This reduces data transferred for a projects-only view.

Project create/edit flow

New Project button -> ProjectView sets projectOpen -> NewProject opens in create mode -> createProject() -> getProjectData() -> local project list refreshes Edit button -> ProjectView stores selected project -> NewProject opens with prefilled state -> updateProject() -> related task.project_name values are synchronized -> projects and tasks paths revalidate

Duplicate project names are checked client-side before mutation, excluding the project currently being edited.

8. Tasks and List View

tasks-overview.tsx owns the task state and shared handlers. It supports filters:

  • All Tasks
  • To Do
  • In Progress
  • In Review
  • Done

The list view uses a deliberately wide table inside an overflow container. This keeps all task fields available on mobile without forcing the whole page to overflow.

Each row supports:

  • Status dropdown.
  • Priority display.
  • Deadline.
  • Edit action.
  • Delete action.

Status changes optimistically update local state, then call editTaskStatus() to persist the change.

9. Kanban Board and Drag/Drop

app/ui/tasks/kanban-board.tsx uses @dnd-kit/core.

Board structure

There are four droppable columns:

Column Meaning
To Do Ready to start
In Progress Currently active
In Review Needs a decision
Done Completed work

Drag flow

PointerSensor detects a drag -> useDraggable identifies task id -> useDroppable identifies target status column -> DragOverlay renders the floating card -> onDragEnd reads over.id -> changeStatus(task.id, nextStatus) -> TaskView updates local state -> editTaskStatus() persists to database

The pointer activation distance is six pixels, preventing accidental drags when clicking a card. The drag handle is separate from edit/delete controls.

10. Schedule Calendar

The old deadline lists were replaced with an interactive month calendar in schedule-overview.tsx.

Calendar behavior

  • Six-week grid always provides stable height.
  • Previous and next month controls update the visible month.
  • Today returns to the current month and selects today.
  • Project deadlines and task deadlines become calendar events.
  • Desktop cells show event labels.
  • Mobile cells show compact event dots.
  • Selecting a day updates the selected-day agenda below.

Date model

Events are normalized into a shared shape with id, title, date, type, priority, status, and project name. dateKey() compares local calendar dates rather than timestamps, avoiding time-of-day mismatches.

11. Search

app/ui/searchbox.tsx is a command-style workspace search.

  • Loads project and task data in parallel.
  • Searches project names.
  • Searches task names, project names, and descriptions.
  • Groups results into Projects and Tasks.
  • Shows contextual metadata such as type, priority, status, and project.
  • Supports Enter to open the first result and Escape to close.
  • Uses loading skeletons and a no-results state.

Search navigates to the relevant section rather than attempting to duplicate project/task detail pages.

12. Theme Toggle

app/components/theme-toggle.tsx toggles the explicit dark class on the root document element.

  • Uses a moon icon in light mode and sun icon in dark mode.
  • Persists the preference as planora-theme in localStorage.
  • Uses useSyncExternalStore to avoid state-in-effect lint problems.
  • Root initialization reads saved preference or system preference.
  • globals.css defines Tailwind's explicit dark variant.

The theme initialization script is placed inside body, not directly inside html, because a script cannot be a child of the HTML element in React's document tree.

The dashboard shell uses independent scrolling: the sidebar is constrained to viewport height, while the main content scrolls separately. This prevents long task pages from pushing the account panel out of view.

14. Loading and Performance

  • Dashboard, projects, tasks, and schedule have route-level loading.tsx files.
  • Loading screens mirror the actual destination geometry instead of using one generic skeleton.
  • Independent database requests use Promise.all().
  • Auth session lookup is request-memoized with React cache().
  • Projects use aggregate progress data rather than loading all tasks.
  • Production is checked with npm run build; development mode is slower because Next compiles routes on demand.

15. Main Data and Mutation API

Function Purpose
getUser() Request-cached authenticated user.
getProjectData() Current user's projects.
getProjectProgress() Grouped total/completed task counts by project.
createProject() Insert project for authenticated user.
updateProject() Update project and synchronize related task project names.
deleteProject() Delete user-owned project.
getTaskData() Current user's tasks.
createTask() Insert task with project relation and copied project name.
editTask() Update task fields and project relation.
editTaskStatus() Persist list/Kanban status changes.
deleteTask() Delete user-owned task.

Mutations call getUser() and reject unauthenticated requests. Database filters include the current user id for updates and deletes.

17. How to Read the Code

  1. Start at a route page such as app/dashboard/tasks/page.tsx.
  2. Read its layout to understand shared navigation and header composition.
  3. Read the page data calls and identify which server actions provide the props.
  4. Open the client component that owns local state, for example tasks-overview.tsx.
  5. Follow callbacks into lib/actions/actions.ts to see how mutations reach the database.
  6. Check the matching loading file to understand the intended loading geometry.
  7. Use db/schema.ts and lib/types/types.ts to understand data shapes.

18. Known Design and Engineering Notes

  • Task data stores both project_id and project_name. Project rename logic synchronizes the copied name on related tasks.
  • The schedule calendar derives events from task and project deadlines; it does not create a separate calendar table.
  • The Kanban board changes task status rather than persisting card order within a status column.
  • The search modal loads the complete current user's project/task lists when opened. For very large accounts, a server-side search endpoint would scale better.
  • Current demo login depends on the test account existing in the database.
  • Production builds have been verified during development, but browser-level interaction tests would provide additional confidence for OAuth and drag/drop.
